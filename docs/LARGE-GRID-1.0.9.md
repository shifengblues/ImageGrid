# 大图与高清预览验证

日期：2026-11-08。Windows 版本 1.0.9，网页版 1.0.1。

## 修改与复现

- 旧版网页版以输出像素数乘 12 再加最大源图缓冲估算，固定 512MB、16384px 拦截。25 张 UHD 图片会被提示约 2441MB，根本未进入实际分配。
- Windows 旧版固定 768MB 拦截，25 张 UHD 图片会因约 1585MB 的估算而拒绝。
- 两端均先增加复现检查，确认失败后移除这些软件自定配额。仍检查正整数、格式/缓冲可表示范围；网页在实际创建画布时验证末像素可读写，避免浏览器不支持的尺寸悄悄生成空图。
- 网页原像素 PNG 逐批扫描线送入 zlib，避免另造完整过滤像素数组和最终编码数组；临时画布结束后主动释放，逐张解码，不同时展开全部源图。不等于完整的磁盘流式拼图，仍需要输出画布或原像素缓冲。

## 真实 5×5 导出

使用 25 张不同内容的 3840×2160 PNG，包含渐变和一像素黑白棋盘，内部间距 3px。目标为 19212×10812（207720144 像素），一份四通道像素约 792MiB / 831MB。

- Chrome：自动填满 PNG、JPG 导出成功；原像素 PNG 分批编码成功。
- Windows 上的 WebKit 引擎：自动填满 PNG、JPG 导出成功。
- Windows 图像核心：实际 PNG/JPG 导出成功；PNG 对全部 25 张源图逐行逐像素比较一致。
- 网页 PNG 下载后重新解码，核对全部 25 个区域与源图 RGBA 完全一致；JPG 重新解码核对完整输出尺寸。
- Windows 最终单文件 EXE 在隔离目录通过 --verify，验证原生解码器、实际窗口的导出、进度与错误恢复。

测试机器约 96GB 内存，不能据此推定所有低内存设备都能处理相同任务。测试素材是合成图片，文件体积和耗时不代表任意照片/插画。真正耗尽内存时，系统可能直接结束进程，错误捕获无法保证兜底。

## 高清预览

旧网页始终用 640px 缩略图，即使点 100% 也不换图。现在根据可见区域和显示大小逐张请求高清预览，256MiB 缓存按需回收，离屏被回收的图片恢复小预览。

此外修复 50% 居中布局与 CSS 变换分别产生半像素定位的问题：图像即使已加载 3840px，屏幕仍可能把一像素黑白棋盘混成灰色。改为从左上角定位、100% 时对齐物理屏幕像素，Chrome 与 WebKit 截图均能保留逐像素纯黑/纯白，实际加载图片为 3840×2160。

网页端 12 项 Node 检查通过，覆盖大图配额回归、跨压缩块 PNG 像素、高清加载及缓存回收；原有浏览器 16 项主流程检查通过。Windows 94 项常规检查通过，另有大图 PNG/JPG 及策略回归。未进行 macOS 实机 Safari 检查。

## 版本边界

取消固定配额不是“无限大小”承诺。浏览器画布、编码格式、数组/行缓冲、磁盘空间、物理内存仍有实际限制。PNG 保留常见 8 位解码像素；JPG 为有损格式；透明度与色彩管理边界延续原说明。
